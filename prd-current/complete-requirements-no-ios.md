# DishFlow 完整产品需求文档（不含 iOS）

版本：v1.0  
基线日期：2026-08-01  
需求来源：当前仓库的 Go API/Worker、React 管理后台、微信原生小程序、MySQL 迁移、OpenAPI 契约及自动化测试  
文档用途：交给模型或开发团队，在无人工补充产品规则的情况下复现当前系统的完整能力

## 0. 阅读与实施约定

### 0.1 需求解释优先级

1. 本文档描述的业务规则和验收标准。
2. `openapi/openapi.yaml` 中的 HTTP 契约。
3. 当前数据库迁移所表达的数据约束。
4. 当前界面仅作为信息架构与交互参考，不允许以“页面上没有显示”为理由省略服务端校验。

如本文档与历史的“单店重写需求”冲突，以本文档为准。系统现状已经是多门店、多租户产品，不再是单店原型。

### 0.2 明确排除范围

- 不实现、不修改、不测试、不交付 `apps/ios` 下的任何内容。
- 不提供原生 iPhone/iPad 客户端，也不要求 Swift、SwiftUI、Xcode 工程或 App Store 发布能力。
- 不做第三方外卖配送、骑手调度、桌位预订、拼团、秒杀、储值、会员等级、积分抵现、部分退款、订单拆单/并单。
- 不把开发环境的 mock 支付或 mock 云打印当作生产支付/打印的替代品。

### 0.3 必须交付的应用

- Go 模块化单体 API，可执行 `serve`、`worker`、`migrate`、`healthcheck`。
- React + TypeScript + Vite 管理后台，同时支持平台管理与门店运营。
- 微信原生 TypeScript 小程序，支持堂食扫码和到店自取。
- MySQL 8 持久化、Redis 会话/短期报价、OpenAPI 3 契约、数据库迁移与自动化测试。
- 生产部署所需的配置清单、健康检查和数据校验能力。

## 1. 产品概述

DishFlow 是餐饮门店点餐与履约系统。顾客通过微信小程序浏览门店菜单、选规格与加料、领取和使用优惠券、完成堂食或自取下单、支付并查看履约进度；门店员工通过 Web 后台接单、制作、叫号、完成订单，并管理菜单、库存、优惠、会员、桌台、采购物料、支付和打印配置；平台管理员负责门店、后台账号及开店申请。

系统的核心目标如下：

1. 顾客看到的价格、库存、优惠、预约容量和订单状态始终以服务端为准。
2. 下单、库存预占、订单快照、预约容量占用和 outbox 事件在同一数据库事务内完成。
3. 支付与退款只有经过微信验签回调或服务端主动查单确认后才能进入成功状态。
4. 多门店数据严格隔离，平台管理员不能绕过门店角色直接参与日常门店操作。
5. 所有关键写操作可幂等、可审计；外部服务失败后可由 Worker 补偿。

## 2. 系统边界与总体架构

### 2.1 运行组件

- API 进程：提供 `/api/v1`、微信支付回调、媒体代理、健康检查，并可托管管理后台静态文件。
- Worker 进程：每 15 秒执行心跳、释放过期预占、支付/退款对账、outbox 分发、云打印派发与状态轮询；定期关闭回收站恢复窗口。
- MySQL：订单、支付、退款、库存、会员、门店、配置与审计的唯一事务权威。
- Redis：可丢弃基础设施，用于十分钟报价、部分会话/限时状态和 Worker 心跳；Redis 丢失不得伪造交易结果。
- React 管理后台：通过 Cookie 会话访问平台或门店管理 API。
- 微信小程序：通过 AppID 定位门店，通过 Bearer 会话访问顾客 API。

### 2.2 多租户规则

- 商品、订单、促销、优惠券模板、顾客、会员、桌台、物料、采购清单、支付配置和打印配置均归属一个 `store_id`。
- 小程序请求携带 `X-Wechat-Appid`，服务端根据门店唯一 AppID 解析门店，不接受客户端直接指定 `store_id` 绕过绑定。
- 管理端门店接口携带 `X-Store-Id`。服务端必须验证当前后台账号在该门店的成员关系及角色。
- 每个普通后台账号最多归属一家门店；平台超级管理员不参与门店运营。
- 跨门店读取、修改、退款、打印、会员调整或引用资源必须返回拒绝，不能通过猜测 ID 访问。

## 3. 角色与权限

### 3.1 顾客

- 游客可浏览菜单、维护本地购物车、匿名算价和查看可领取优惠券。
- 下单、订单查询、支付、取消、领券、入会和积分兑换前必须完成微信会话确认。
- 只能访问当前门店中属于自己的订单、优惠券和会员数据。

### 3.2 店员 STAFF

- 可访问订单工作台，查看订单详情并按合法状态推进履约。
- 可访问物料买菜；允许参与草稿清单明细和已提交清单的金额回填等协作操作。
- 不可访问经营分析、历史订单、菜单、优惠、门店配置、支付、成员管理和退款管理。

### 3.3 店长 MANAGER

- 拥有店员权限。
- 可访问历史订单、经营分析、客户会员、菜单与定价、优惠、桌台、门店设置、备份导出、退款异常、成员只读/审批范围、小程序配置、云打印和物料管理。
- 可接单与履约、发起门店主动全额退款、审核顾客已接单取消申请、管理菜单/库存/优惠/桌台、调整会员积分、管理打印机。
- 不可导入覆盖门店数据，不可管理真实支付密钥，不可切换支付 mock，不可删除门店成员或云打印机，不可永久删除优惠券模板。

### 3.4 店主 OWNER

- 拥有店长权限。
- 可导入门店备份、配置微信支付和小程序 AppSecret、开关 mock 支付、管理门店成员角色、移除成员、删除云打印机、永久删除满足条件的优惠券模板。
- 高风险操作必须二次确认并记录审计日志。

### 3.5 平台超级管理员

- 仅能访问平台门店、后台用户和开店申请审批。
- 可创建、改名、启停门店，创建/编辑后台账号，指定唯一店主，审批开店申请。
- 不可进入订单、菜单、会员、支付等门店运营页面；如需运营必须使用具有门店成员身份的普通账号。

## 4. 顾客微信小程序需求

### 4.1 启动、门店定位与身份

1. 普通入口默认进入当前 AppID 对应门店的“到店自取”菜单，并清除过期桌台上下文。
2. 扫描桌台小程序码时，从 `scene` 解出不透明桌码 token，服务端解析为启用桌台；成功后锁定为堂食及该桌号。
3. 桌码无效、已轮换或桌台停用时，不允许创建堂食报价，应提示重新扫码。
4. 小程序启动时读取 storefront bootstrap、门店状态和品牌配置，包括门店名、品牌名、主题色、Logo、营业状态。
5. 浏览和加购无需头像昵称授权。需要顾客身份时调用 `wx.login`，以 code 换取门店范围内的业务会话。
6. 微信登录需要门店 AppID 与服务端保存的 AppSecret；任何密钥不得下发到小程序。

### 4.2 菜单浏览

- 展示门店营业/休息状态、公告、当前用餐方式和桌号。
- 支持在堂食与自取之间切换；扫码桌码后堂食方式锁定，不允许手工切换为其他桌台。
- 左侧或等效结构展示启用分类，分类按 `sort_order` 排序。
- 菜品展示图片、名称、描述、起售价、可选加料数量、售罄状态。
- 支持按菜品名称、描述或口味相关文本搜索。
- 只有分类启用、菜品启用、未进入回收站且至少一个 SKU 可售的菜品可购买。
- 图片只允许可信 HTTP(S) 地址；COS 菜品图片通过 API 媒体代理展示，禁止 `javascript:`、`data:` 等不安全来源。

### 4.3 SKU、选项与购物车

- 每个菜品至少有一个 SKU；SKU 包含名称、价格、启用状态、库存模式、排序和默认项。
- SKU 可以是无限库存或每日库存。每日库存显示当前目标业务日剩余数量。
- 选项组支持单选或多选，包含是否必选、最少/最多选择数、排序和默认选项。
- 选项项包含名称、加价、启用状态、排序和默认状态。
- 单选组最多一个默认项；多选组默认项数量不能超过最大选择数；默认项必须启用。
- 同一 SKU、同一组选项 ID 的购物车项自动合并；选项顺序不影响购物车行身份。
- 单行数量为 1～99；数量降为 0 时删除。
- 购物车只在本地保存 SKU ID、选项 ID、数量，不保存可信价格。
- 刷新菜单时清理已下架、售罄、规格或选项失效的购物车行，并明确告知顾客。

### 4.4 服务端算价

1. 唯一算价入口是 `POST /pricing/preview`。
2. 请求包含场景、购物车项；堂食附桌码 token，自取预约时附服务端签发的 RFC 3339 时间；选券时附顾客券 ID。
3. 客户端不得提交或覆盖单价、包装费、折扣、应付金额。
4. 服务端重新加载目标业务日的 SKU、选项、库存、满减和优惠券。
5. 报价返回商品行、商品金额、包装费、折扣明细、应付金额、不可用优惠券原因、取餐类型、预约时间、十分钟过期时间和 `quote_token`。
6. `quote_token` 绑定门店、顾客/匿名主体、场景、桌号、购物车摘要、优惠结果、预约时间和过期时间。
7. 商品、选项、库存、桌码或预约时段不合法时不得生成可下单报价。
8. 门店休息时可浏览，但不可结算。

### 4.5 价格规则

- 所有金额使用 `int64` 分，UI 仅负责把分格式化为元。
- 行单价 = SKU 基础价 + 所选有效选项加价。
- 商品金额 = 所有行单价 × 数量之和。
- 自取包装费 = 每个菜品/SKU 所属菜品的每份包装费 × 数量；堂食包装费为 0。
- 系统选择满足门槛且处于有效期内的最优满减。
- 优惠券必须属于当前顾客和当前门店，状态为可用，模板启用，且满足有效期和最低消费。
- 当前生产算价比较“最优满减折扣”和“指定优惠券折扣”，默认只采用优惠金额更大者，不叠加；金额相同时采用满减。
- 折扣不应使应付金额低于 0。
- 0 元订单仍必须经服务端创建并确认支付成功，但不调用微信收款。

### 4.6 结算与预约自取

- 结算页展示用餐方式、桌台/自取信息、菜品快照、优惠、包装费、实付金额和最多 100 字备注。
- 堂食必须来自有效桌码，且不允许携带预约时间。
- 自取默认“尽快取餐”，可切换为“预约取餐”。
- 预约配置包括：开关、可预约天数 1～30、最少提前 0～1440 分钟、时段间隔 5～120 分钟、每时段容量至少 1、预计制作时间 1～180 分钟。
- 门店营业时间当前只支持单个 `HH:mm-HH:mm` 且结束晚于开始，不支持跨午夜。
- 日期范围从门店当地“今天”起，包含今天，共 `pickup_advance_days` 天。
- 时段从营业开始按固定间隔生成，开始时间必须严格晚于“当前门店时间 + 最少提前分钟数”。
- 每个时段展示标签、容量、剩余单数和是否可选。历史、约满或截止时段不可选。
- 报价阶段校验时段；创建订单时必须在数据库行锁下再次原子占位，最后一个名额被并发抢占时返回 `PICKUP_SLOT_FULL`。
- 每个已使用时段保存容量快照。以后修改门店配置不追溯现有订单。
- 预约订单使用预约日期的每日库存；即时订单使用门店当前业务日库存。
- 切换日期、时段或优惠券后必须重新报价。报价过期必须重新确认金额和容量。

### 4.7 创建订单与库存

- 创建订单只信任有效 `quote_token`；请求中的购物车若存在，必须与报价摘要一致。
- 创建订单、写入不可变商品/规格/选项/价格快照、预占库存、占用预约容量、生成订单事件和 outbox 必须同事务提交。
- 待支付订单预占库存十分钟。支付成功后预占转为已售；超时或成功取消时释放预占。
- 库存变更记录流水，且以订单保存的 `pickup_business_date` 为准，不能使用数据库当前日期推断。
- 订单生成门店业务日内自增取餐号，格式至少三位（001、002），超过 999 时自然扩展；历史遗留订单可无取餐号。
- 同一 quote 只能创建一个订单；重复请求需由 `Idempotency-Key` 和唯一约束返回同一结果或明确冲突。

### 4.8 支付

- 待支付订单可创建或复用未过期 `prepay_id`，有效时间接近结束时拒绝继续支付。
- 真实支付使用微信支付 v3 小程序/JSAPI 参数，客户端调用 `wx.requestPayment`。
- 顾客取消微信支付时保留待支付订单，并可从订单详情继续支付。
- 小程序不能仅根据 `wx.requestPayment` 成功回调显示已支付；必须轮询/查询服务端订单，直到服务端支付状态为成功或明确失败/关闭。
- 开发或门店 mock 模式下，预支付明确返回 `mock_payment=true`，小程序再调用确认接口；不得把任意非支付响应当作 mock 成功。
- mock 订单和退款永久保留测试标记。

### 4.9 支付结果、订单列表与详情

- 支付结果页展示成功、确认中或失败状态；成功后展示取餐号/桌号、预约时间和本单所得积分。
- 订单列表支持全部、待支付、制作中、待取餐、已完成、已取消筛选。
- 每张订单卡展示订单号、取餐方式、预约标签、菜品摘要、金额、状态和时间。
- 支持“再来一单”：以当前菜单重新匹配历史 SKU/选项；失效项必须提示重新选择，不得静默替换。
- 订单详情展示履约状态、取餐号、桌号/自取、预约时间、预计时间、商品价格快照、金额拆分、支付状态、下单/支付时间、备注和事件时间线。
- 历史订单始终展示下单时快照，不受后来改名、改价、删除影响。

### 4.10 顾客取消与退款申请

- `PENDING_PAYMENT`：先查微信订单避免“已扣款但本地未更新”；确认未支付后关闭微信订单并取消，释放库存/预约容量。
- `PAID` 且门店未接单：顾客取消后自动发起全额退款。
- `ACCEPTED`：创建待人工审核的取消/退款申请，订单进入 `CANCEL_REQUESTED`，返回已受理。
- `CANCEL_REQUESTED` 或 `REFUNDING`：重复取消返回处理中，不生成第二张退款单。
- `PREPARING` 及以后：顾客不能自行取消；店长/店主仍可在后台发起门店主动全额退款。
- 退款成功后释放预约容量最多一次；库存是否回补遵循当前订单退款实现，不允许重复流水。

### 4.11 优惠券

- 优惠券中心包含可使用、领券中心、已使用、已过期。
- 公开领取仅展示模板启用、公开领取、处于有效期且顾客尚未领取的一次性模板。
- 领取接口必须幂等，不能因重复点击生成重复券。
- 券展示名称、满减金额、最低消费、范围和有效期。
- 下单成功核销实际采用的顾客券；未被采用的指定券不得核销。

### 4.12 会员与积分

- 游客点单不受入会影响。入会需勾选会员协议/隐私政策并通过微信 `getPhoneNumber` 获得一次性手机号 code。
- 服务端调用微信接口验证手机号；手机号加密保存，同时保存门店范围的不可逆 hash、后四位和区号。
- 同一门店同一手机号只能绑定一个顾客；重复入会返回现有会员，不重复发新人礼。
- 会员号在门店范围唯一且稳定，会员状态为 `ACTIVE` 或 `FROZEN`。
- 门店配置每消费 1 元积分数，计算规则是先对实付分数向下取整到整元，再乘积分比例。
- 支付成功时仅给已入会且正常会员入账一次；退款成功时按原订单所得积分扣回一次。
- 积分余额、支付入账、退款扣回、积分兑券和人工调整必须有不可变流水及 `balance_after`。
- 积分兑换只展示已启用、有效期内、开放兑换且积分成本大于 0 的券模板。
- 兑换必须事务性扣减积分并发券，支持重复兑换但每次请求幂等；余额不足不得出现负数。
- 入会新人券只有在配置的模板当前有效时发放一次；未配置或模板失效不阻止入会。

### 4.13 “我的”与门店信息

- “我的”页展示会员号、积分余额、新人礼提示，并提供订单、优惠券、联系门店、门店信息与政策入口。
- 门店信息展示营业状态、营业时间、地址、电话、隐私/退款政策和资质信息。
- 可调用微信地图和拨号能力；缺失地址或电话时给出友好提示。

## 5. 管理后台通用需求

### 5.1 登录与会话

- 使用账号密码登录，密码以强哈希保存；新密码长度 12～72。
- 登录同时按客户端 IP 和标准化账号限速。
- 管理会话使用 Secure、HttpOnly、SameSite Cookie；空闲 8 小时过期，绝对最长 7 天，活跃续期最频繁每 30 分钟一次。
- 退出登录先撤销服务端会话再清 Cookie；过期 Cookie 的退出仍需幂等成功。
- 会话中断收到 401 时统一回到登录页，不能继续展示可写状态。

### 5.2 壳层与门店切换

- 桌面端侧栏、移动端抽屉，按角色只显示有权访问的菜单。
- 壳层保留门店选择兼容能力；按当前产品规则，普通账号只能绑定一家门店，因此正常情况下直接展示唯一门店。若迁移数据中存在多个关系，切换后必须清空/失效所有旧门店查询缓存。
- 显示当前门店营业状态、当前用户、角色和退出入口。
- 门店启用 mock 支付时全局显示醒目警告。
- 没有门店关系的普通账号只进入“开店与加入”。

## 6. 门店履约与订单管理

### 6.1 订单工作台

- 默认首页为订单工作台，不是统计大屏。
- 展示 `PAID`、`ACCEPTED`、`PREPARING`、`READY` 四列，分别提供接单、开始制作、出餐/待取餐、完成操作。
- 自动每 3 秒轮询，支持手动刷新；可按订单号、取餐号、桌号搜索。
- 即时单优先，预约单按 `scheduled_for` 升序；卡片醒目展示预约时间。
- 使用门店 `pickup_minutes` 计算超时阈值，超时订单标红并只提醒一次。
- 新支付订单和新超时订单支持声音提醒、音量调节和试听；首次加载不得把已有订单全部当作新单提醒。
- 订单详情包含商品快照、金额、备注、支付/退款标记、事件时间线、本地打印、云打印、合法下一步和退款入口。
- 每次状态推进携带 `expected_version`，服务端以当前状态 + 版本做乐观锁；两名员工同时操作只允许一个成功。

### 6.2 订单状态机

主链路：

`PENDING_PAYMENT → PAID → ACCEPTED → PREPARING → READY → COMPLETED`

取消与退款分支：

- `PENDING_PAYMENT → CANCELLED`
- `PAID → REFUNDING → REFUNDED`
- `ACCEPTED → CANCEL_REQUESTED → ACCEPTED`（驳回）
- `CANCEL_REQUESTED → REFUNDING → REFUNDED`（通过）
- `ACCEPTED/PREPARING/READY/COMPLETED → REFUNDING → REFUNDED`（门店主动退款）

禁止跳级、回退或以客户端状态覆盖服务端状态。支付状态和退款状态是独立维度，不能用履约状态代替。

### 6.3 历史订单

- 默认查询时间范围，支持开始/结束时间、多个履约状态、场景、支付状态、订单号/取餐号/桌号。
- 采用稳定游标分页，支持上一页、下一页。
- 支持按当前筛选导出 CSV；导出必须受门店权限约束。
- 详情中可查看价格快照和完整事件，可由店长/店主对允许状态发起全额退款，退款原因必填或使用明确默认值。

### 6.4 退款与异常

- 退款列表聚合自动退款、审核退款和门店主动退款，显示退款号、订单号、金额、原因、状态和测试标记。
- 已接单顾客取消必须由店长/店主显式通过或驳回；通过后发起全额退款，驳回后订单恢复 `ACCEPTED`。
- 支付/退款异常列表自动刷新，显示业务号、错误类型、状态、错误信息、重试次数和发生时间。
- “重试查单”只把补偿任务加入队列，最终状态仍需微信查单确认。

## 7. 商品、库存与营销后台

### 7.1 分类

- 分类字段：名称、启用状态、排序。
- 启用分类排在停用分类前；支持新建、改名、排序和启停。
- 删除分类为 30 天软删除，同时把该分类下未删除菜品放入同一删除批次并下架。
- 30 天内恢复分类时，恢复同批次菜品及其删除前启用状态。
- 恢复窗口结束后仅关闭恢复能力，底层行保留 tombstone 以保护历史外键。

### 7.2 菜品

- 字段：编码、名称、分类、描述、图片、排序、上/下架、人工售罄、每份自取包装费、SKU 列表和选项组列表。
- 图片上传后保存可信 URL；允许 JPEG/PNG/WebP，完整解码后大小不超过 2 MB，尺寸不超过 4096×4096 且不超过 1600 万像素。
- SKU 字段：名称、价格、库存模式、每日库存、启用、排序、默认。
- 选项组字段：名称、单/多选、是否必选、最小/最大选择数、排序；选项项含名称、加价、启用、排序和默认。
- 删除菜品进入 30 天回收站；恢复菜品前所属分类必须已恢复。
- 改名、改价、删除不得改变历史订单快照。

### 7.3 库存调整

- 对每日库存 SKU 支持正数增加、负数扣减，调整原因为必填。
- 调整必须验证不会使可用库存违反已预占 + 已售约束。
- 请求必须带幂等键，写库存流水和审计日志。
- 人工售罄优先于剩余库存；无限库存不应因每日库存表缺失被判售罄。

### 7.4 满减与优惠券模板

- 满减字段：名称、门槛、减免额、适用范围、开始/结束时间、启用、叠加策略。
- 优惠券模板字段：名称、最低消费、减免额、范围、开始/结束时间、启用、公开领取、人群、积分兑换开关和积分成本。
- 人群支持：全部、新客、老客、近 180 天活跃、近 180 天沉默。
- 支持按人群立即发放，发放过程必须避免同一次任务重复发券。
- 店主只能永久删除从未发放、未被引用为新人券等安全条件成立的模板；否则返回可理解的冲突原因。店长不能永久删除。
- 试算和生产订单必须调用同一算价领域逻辑。

## 8. 会员与客户后台

### 8.1 会员管理

- 会员概览展示已加载人数、积分余额合计和累计净消费。
- 门店可设置每元积分和有效新人券模板。
- 列表支持按会员号前缀或手机号后四位查询，展示积分、订单数、累计净消费、最近消费、入会时间和状态。
- 详情展示脱敏手机号、积分、消费统计和积分流水。
- 店长/店主可人工调整积分；delta 不得为 0、原因必填、余额不得小于 0，操作幂等且审计。
- 后台永不返回完整手机号明文。

### 8.2 客户洞察

- 经营口径以支付成功金额和退款成功金额为准。
- 展示新客/老客构成、客户数、支付订单数、实收、退款、净收、客单价，并与等长前一周期比较。
- 近 180 天 CRM 展示已下单、活跃、沉默、新客、老客、下单频次分布、活跃客户排行和沉默客户待唤醒列表。
- 客户行为数据按门店隔离，不返回微信 openid 等敏感原始标识。

## 9. 经营分析

- 支持自定义日期范围和快捷区间；时间按门店时区解释。
- 指标包括支付金额、退款金额、净收入、支付订单数、退款订单数、客单价、客户数、新客和老客。
- 趋势支持按日；单日范围可切换按小时。
- 分布包括堂食/自取场景、24 小时时段、热销商品的数量和金额。
- 退款成功应从净收入扣除；处理中或失败退款不得提前扣除。
- 对比百分比在基期为 0 时返回空或明确语义，不能制造无穷值。

## 10. 桌台、门店与入驻

### 10.1 桌台

- 桌台字段：桌号、区域、启用状态；同门店桌号唯一。
- 新建/编辑后可生成微信官方小程序码，不允许用普通二维码伪装。
- 换码会生成新的高熵不透明 token 和小程序码，并原子替换；旧码立即失效。
- 小程序码存储在私有 COS；数据库只保存对象 key。下载接口需验证门店权限。
- scene 必须满足微信长度/字符限制，不能包含门店敏感数据。

### 10.2 门店设置

- 字段：门店名称、电话、地址、营业时间、预计取餐分钟数、预约配置、公告、营业开关、时区。
- 关闭营业后仍可浏览菜单和历史订单，但禁止新订单结算。
- 关闭预约只影响新报价/新订单，不取消已有预约订单。

### 10.3 小程序配置

- 每店唯一微信 AppID、品牌名称、主题色和 Logo。
- AppID 冲突必须拒绝；AppSecret 只能在安全中心写入，不能在小程序配置接口回显。

### 10.4 开店与加入

- 无门店账号可提交开店申请：拟开门店名、联系方式。
- 无门店账号可按门店 ID 提交加入申请并选择店员/店长/店主角色。
- 申请状态为 `PENDING/APPROVED/REJECTED`，保留提交、审批时间、审批人和备注。
- 平台管理员审批开店：通过时创建门店并把申请人设为店主；处理必须事务性且不可重复创建。
- 门店店主审批加入：通过时建立唯一成员关系；驳回不赋权。
- 店主可变更成员角色和移除成员。把某成员设为 OWNER 时，其他 OWNER 自动降为 MANAGER，以保持唯一店主；移除当前店主前应先完成所有权转移，避免门店失去管理入口。

### 10.5 平台管理

- 门店：创建、改名、启停，展示时区、品牌和 AppID 状态。
- 用户：创建登录账号、显示名、初始密码、启停、平台超管标记；登录账号不可在编辑时随意更换。
- 指定店主：普通账号只能绑定一个门店，冲突时必须先解除旧关系。
- 平台账号操作写平台级审计日志。

## 11. 门店数据导入导出

- 可选择导出基础信息、菜单、小程序配置，文件格式标识为 `dishflow.store-export`，当前版本为 1。
- 文件包含导出时间、来源门店 ID、分区和数据；不包含支付/打印密钥、订单、顾客、会员、库存流水或审计日志。
- 店长和店主可导出；只有店主可导入。
- 导入文件最大 1.5 MB，只接受 JSON 和受支持版本；导入前先在客户端预览来源、分区及菜单数量，服务端仍需完整校验。
- 可选择分区；小程序 AppID 默认保留目标门店，只有显式开关才覆盖，且必须检查全局唯一冲突。
- 菜单策略固定为 replace：现有菜单进入可恢复回收站，新分类/菜品/SKU/选项以新 ID 创建。
- 导入基础信息、菜单和小程序配置应在事务内应用；失败不得留下半套菜单。
- 导入属于不可撤销高风险操作，UI 必须二次确认并说明影响。

## 12. 物料买菜

### 12.1 物料目录

- 字段：名称、图片、分类、单位、默认数量、备注、启用状态、排序；同门店名称唯一。
- 支持搜索、分类筛选、卡片/表格切换、新增、编辑、启用和停用。
- 停用物料不影响采购清单中的名称/单位快照。

### 12.2 采购清单

- 清单号按门店与业务日顺序生成；字段含业务日期、标题、状态、总金额、版本、打印次数和操作人/时间。
- 状态机：`DRAFT → SUBMITTED → PRINTED → COMPLETED`，任何未完成状态可按权限进入 `VOID`；禁止非法回退。
- 草稿可添加物料、批量添加当前筛选结果、修改数量/备注、移除条目；重复物料不得重复加入。
- 清单项保存物料名称和单位快照，数量支持两位小数且必须大于 0。
- 提交要求至少一个条目。提交后可本地标记打印或发送默认云打印机。
- 支持回填本次合计消费金额；当前产品以清单汇总金额为主要录入，不要求逐项实际单价。
- 完成前要求金额信息完整；作废需可选原因。
- 所有状态变更带版本号、记录事件和操作者；并发修改只有一个成功。

## 13. 云打印

### 13.1 配置与设备

- 每店独立配置商鹏 `appid/appsecret`，密钥 AES-GCM 加密，读取接口只返回是否已配置。
- 配置状态：`draft/ready/disabled`。只有 AppID 和 AppSecret 完整且未禁用时为 ready。
- 支持门店级显式模拟打印开关；模拟开启时不调用商鹏或真实设备。
- 打印机字段：SN、写入型 KEY、名称、默认、份数 1～5、启用、在线状态、备注。
- 店长/店主可绑定、编辑、设默认、测试和刷新；只有店主可删除。

### 13.2 打印任务

- 类型：订单自动打印 `order`、测试 `test`、手动重打 `reprint`、采购清单 `purchase`。
- 状态：`QUEUED → SENDING → SUBMITTED → PRINTED`，失败进入 `FAILED`。
- 订单支付事务写 `order.paid` outbox；开启自动打印并存在默认打印机时，Worker 生成 58mm 小票并发送。
- 手动云打印从订单详情触发；浏览器本地打印仍保留并使用 80mm 打印样式。
- 小票包含门店、堂食桌号或自取号、预约自取完整时间、商品/规格/选项、数量、备注、金额和测试标识。
- Worker 轮询商鹏状态；任务日志保留关联单号、打印机、商鹏 ID、尝试次数、错误和时间。
- 同一订单自动打印需去重。打印失败不得改变支付结果。
- 当前实现中打印确认可把仍为 `PAID` 的订单推进为 `ACCEPTED`；其他状态不得被打印轮询越级修改。

## 14. 微信支付与退款配置

### 14.1 每店配置

- AppID 来自小程序配置；安全中心配置 AppSecret、商户号、商户证书序列号、APIv3 密钥、商户私钥，以及微信支付验签材料。
- 推荐微信支付公钥模式：`PUB_KEY_ID_*` + `pub_key.pem`；兼容已有商户的平台证书模式。
- 上传 `apiclient_cert.pem` 仅在浏览器解析商户号、序列号和公钥，不保存证书文件本身。
- 浏览器校验商户私钥是否与商户证书匹配，服务端还需验证 PEM 和必要字段。
- 密钥字段只写不读：空值表示保留，非空覆盖；接口、日志和审计不得返回明文。
- 就绪检查包括 AppID、商户号、序列号、APIv3、商户私钥和至少一种微信验签材料；也要单独显示小程序登录是否就绪。
- 状态自动为 draft/ready，也可由店主强制 disabled。

### 14.2 支付回调

- 回调路径包含门店 ID，必须检查路径门店与订单门店一致。
- 验证微信签名、证书/公钥 ID、时间窗口，AES-GCM 解密通知。
- 核对 AppID、商户号、商户订单号、金额、币种和交易 ID。
- provider event ID 与业务状态双重幂等；重复回调返回一致成功，不重复扣库存、发积分、打单。
- 成功处理后更新 payment、订单、库存、积分、优惠券和 outbox，相关写入同事务。

### 14.3 退款

- 当前只支持全额退款，一单最多一个有效退款意图和唯一商户退款号。
- 先落本地退款意图，再调用微信；调用失败保留可补偿状态。
- 回调或主动查单核对订单号、退款号、微信退款 ID、金额、总额和币种。
- 只有微信 `SUCCESS` 才显示退款成功并把订单推进 `REFUNDED`；`PROCESSING` 继续等待，异常进入 `ABNORMAL`。
- 退款成功扣回本单会员积分且只执行一次。

### 14.4 Mock 支付

- 只有店主可切换；开启时必须输入确认词 `MOCK`，关闭也需确认。
- `SHOP_DEV_MODE=true` 时服务端始终可使用 mock，后台需明确警告。
- mock 只用于联调；所有订单和退款仍走真实数据库状态机、库存、积分、outbox 和审计。

## 15. Worker 与可靠性任务

- 每 15 秒写 Redis `worker:heartbeat`，TTL 45 秒。
- 释放过期待支付订单库存预占和预约容量，操作幂等。
- 对支付 `PREPAY_CREATED/未知` 状态主动查单；成功记账，关闭/撤销/支付错误则关单，未支付过期时先调用微信关单。
- 对退款 `CREATED/PROCESSING/异常待重试` 主动发起或查单，指数或受控延迟重试。
- 分发 outbox，失败保留未投递记录。
- 消费支付成功事件执行自动云打印，轮询已提交打印任务。
- 每小时关闭一次超过 30 天的菜单回收站恢复窗口；失败时缩短重试间隔。
- 任何外部 API 调用不得在持有数据库行锁的长事务中执行。

## 16. API 通用约定

- 业务 API 前缀 `/api/v1`；JSON 使用 `snake_case`。
- 成功直接返回业务对象或 `{items,next_cursor,total}`；错误统一为 `{code,message,request_id,details}`。
- 所有关键写接口接受 `Idempotency-Key`；同主体同 key 同请求返回已保存结果，不同请求体返回冲突。
- 管理端使用 Cookie + `X-Store-Id`；小程序使用 Bearer token + `X-Wechat-Appid`。
- 列表排序稳定，分页方式不能在同一资源中混用。
- 请求 ID 只接受安全字符和有限长度；无可信请求 ID 时服务端生成。
- OpenAPI 是客户端/服务端共享契约；接口实现、Go DTO 和 TypeScript 类型必须一致。
- 主要错误必须可操作，例如 `QUOTE_EXPIRED`、`QUOTE_MISMATCH`、`TABLE_NOT_FOUND`、`TABLE_DISABLED`、`PICKUP_SLOT_FULL`、`PICKUP_TIME_INVALID`、`STATE_CONFLICT`、`PAYMENT_UNAVAILABLE`、`REFUND_CONFLICT`、`INSUFFICIENT_POINTS`、`WECHAT_APPID_CONFLICT`。

## 17. 数据与一致性要求

### 17.1 关键实体

- 身份：`customers`、`customer_sessions`、`admin_users`、`admin_sessions`、`shop_members`。
- 门店：`stores`、`dining_tables`、开店/加入申请、小程序/支付/打印配置。
- 菜单：`categories`、`products`、`skus`、`option_groups`、`option_items`。
- 营销会员：`promotions`、`coupon_templates`、`customer_coupons`、`customer_memberships`、`member_points_ledger`。
- 交易：`orders`、`order_items`、`order_events`、`payments`、`refunds`。
- 库存预约：`daily_inventory`、`inventory_reservations`、`inventory_movements`、`pickup_slot_capacity`。
- 采购打印：`materials`、`purchase_lists`、`purchase_list_items`、`purchase_list_events`、`cloud_printers`、`cloud_print_jobs`。
- 可靠性：`idempotency_keys`、`webhook_events`、`outbox`、`audit_logs`。

### 17.2 不变量

- 金额非负；库存满足 `available_qty >= reserved_qty + sold_qty`。
- 预约占用满足 `0 <= reserved_orders <= capacity_snapshot`。
- 订单 quote 唯一、支付一单唯一、有效退款一单唯一。
- 取餐号在门店 + 业务日内唯一。
- AppID 全局唯一；桌号、物料名、会员号和手机号 hash 在各自门店范围唯一。
- 订单项、采购项均保存快照，外部主数据变化不影响历史。
- 所有成功状态推进比较版本；所有回调和补偿允许重复执行而结果不变。

## 18. 安全、隐私与审计

- 生产环境拒绝过短会话/报价签名密钥；凭证加密 key 不得为空。
- 微信回调在验签、时间、解密或身份/金额校验任一未通过时 fail closed。
- 可信代理只来自 `SHOP_TRUSTED_PROXIES`，不能无条件信任转发 IP 头。
- 管理 API 返回安全响应头，敏感响应禁止缓存。
- 日志禁止记录 openid、完整手机号、Cookie/Bearer token、支付密文、私钥、APIv3 key、AppSecret、打印 KEY。
- 关键写入记录操作者、动作、资源、摘要、request_id 和时间；摘要不能原样倾倒含密钥的 JSON。
- 顾客手机号加密保存，后台只显示后四位脱敏值。
- 媒体上传使用随机对象 key，不得把桌码 scene 或敏感标识写入对象名。

## 19. 非功能需求

- 单门店目标峰值 100 RPS、500 并发会话。
- 菜单读取 P95 < 300ms，算价 P95 < 500ms（不含不可控第三方耗时）。
- 健康检查：`/health/live` 只证明进程存活；`/health/ready` 检查 MySQL 与 Redis。
- 数据库每日备份，目标 RPO 24 小时、RTO 4 小时。
- 服务重启、Worker 重启、Redis 清空后，不得丢失已确认订单/支付/退款/积分/库存流水。
- 管理后台需要适配桌面和移动宽度；核心表格在小屏提供紧凑卡片或横向滚动。
- 所有交互提供加载、空数据、失败重试、权限不足和并发冲突状态。
- 时间统一存 UTC 或明确语义，展示和业务日计算使用门店 IANA 时区。

## 21. 端到端验收场景

### A. 堂食扫码闭环

1. 店主配置 AppID/AppSecret，创建 A08 桌台并生成官方小程序码。
2. 顾客扫码后进入对应门店且锁定 A08 堂食。
3. 选择 SKU 和加料，服务端报价不收包装费。
4. 创建订单、支付成功，得到当日门店取餐号。
5. 工作台出现订单；店员依次接单、制作、待取餐、完成。
6. 顾客在订单详情看到相同状态和不可变价格快照。

### B. 即时自取、优惠与库存

1. 设置每日库存 2、每份包装费，创建有效满减和更大金额优惠券。
2. 顾客自取下单 1 份，报价采用更优优惠券并收包装费。
3. 待支付时库存预占，第二位顾客只能看到剩余 1。
4. 支付成功后预占转已售且优惠券核销；改价不影响历史订单。

### C. 预约并发

1. 配置未来时段容量 1，两名顾客均成功获得包含该时段的报价。
2. 两人并发创建订单，只有一人成功，另一人收到 `PICKUP_SLOT_FULL`。
3. 成功订单只占预约目标日库存；取消/超时后容量和库存只释放一次。
4. 后台、小程序订单详情、导出和小票显示同一门店本地预约时间。

### D. 支付迟到与重复回调

1. 顾客发起支付后网络断开，本地订单仍为待支付。
2. 微信成功回调或 Worker 查单使订单进入 PAID。
3. 同一通知重复发送不重复卖库存、发积分、核销券或生成自动打印任务。

### E. 取消审核与退款

1. PAID 未接单订单由顾客取消，自动进入全额退款流程。
2. ACCEPTED 订单取消后进入待审核；店长驳回则恢复 ACCEPTED。
3. 另一单审核通过后退款，只有微信确认 SUCCESS 才显示已退款并扣回积分。
4. 重复点击、重复回调和 Worker 重试不生成第二张退款单。

### F. 会员

1. 游客可正常下单；验证手机号同意协议后入会并获得一次新人券。
2. 重复入会不重复发券，同手机号不能绑定本店另一个顾客。
3. 会员支付后按整元向下取整获得积分；退款扣回同等积分。
4. 积分兑券事务成功，重复请求不重复扣分；余额不足被拒绝。

### G. 菜单回收站与备份

1. 删除分类后分类及子菜品进入 30 天回收站，小程序不再展示。
2. 先恢复分类可连带恢复同批菜品；单独恢复菜品时父分类已删除则被阻止。
3. 导出菜单，修改现有菜单后由店主 replace 导入；旧菜单进入回收站，新菜单可售。
4. 导入文件不含任何密钥；AppID 默认不覆盖，显式覆盖冲突时整次导入失败。

### H. 物料与打印

1. 创建物料和草稿清单，批量加入可见物料且不重复。
2. 提交后通过默认商鹏打印机打印，日志从 SUBMITTED 最终变为 PRINTED。
3. 回填总金额并完成清单；非法状态修改被拒绝。
4. 模拟打印开启时全链路可验收但不触发真实设备，并在后台持续显示警告。

### I. 多租户与权限

1. A 店店长携带 B 店 `X-Store-Id` 访问订单、会员、退款、图片或打印均被拒绝。
2. STAFF 不能访问历史订单、菜单和退款接口。
3. MANAGER 不能导入备份、读写支付密钥或开启 mock。
4. 平台超管只能管理平台资源，不能进入任一门店工作台。

## 22. 当前实现核对提示（供复现者使用）

以下不是降级需求，而是理解当前代码结构时容易误判的点：

- 部分管理路由共用 `emptyPage`/`echoMutation` handler 名称，但仓储层会按资源路由到真实的分类、菜品、促销、优惠券、桌台、用户和门店关系表，并写审计；复现时必须真实持久化，不能只回显请求。
- `admin_resources` 仍用于少量通用管理资源兼容，不应替代订单、菜单、支付等核心关系模型。
- Redis 报价只有十分钟，报价丢失后要求重新算价，不允许尝试从客户端恢复可信金额。
- 管理后台展示了 `stack_policy` 和优惠范围等产品字段；当前核心算价仍以“满减与券择优不叠加”为实际基线。若扩展叠加或范围，必须同时扩展数据库、算价、订单快照和测试，不能只保存表单。
- 云打印、微信支付和微信小程序码都支持开发/模拟路径，但生产必须使用真实凭证并 fail closed。
